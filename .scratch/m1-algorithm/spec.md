# M1 演算法：地面判斷、推薦投放點、投放前確認

Category: enhancement

> `§` 指 [dev_board_spec.md](../../dev_board_spec.md)，Q1～Q8 是 2026-11-24 的討論決定（列在「Implementation Decisions」）。這份 spec 跟 dev_board_spec.md 不同的地方，以這份為準；第一件工作就是把差異改回 dev_board_spec.md。

## Problem Statement

操作員要從空中把物資投放到災民附近，但從畫面上很難判斷地面夠不夠平、旁邊有沒有坑或屋頂邊緣。開發板要能回答三件事：現在離地多高、附近哪裡可以投放、正下方現在能不能投放。

目前只有專案骨架和設定檔，沒有任何判斷功能。H1V1 還沒到，這台電腦也沒有 Gazebo 和 PX4，所以要先用合成深度把演算法做完、驗完，板子到了才來得及。

另外，討論時用小模擬跑 §6.2，發現照現在的規則和驗收方式做會有問題：

- 反投影差半個像素，7.5 m 高時前後、左右各偏約 4.4 cm
- 平地 7.5 m 的誤擋在畫面邊緣算出來是 9.1%，超過 5% 的標準
- 屋頂邊離投放區 0.3 m 以上就可能判合格，外圈沒有保護到應有的距離

## Solution

做一個不碰網路的**判斷核心**：餵姿態、位置、深度幀、按鈕請求和目前時間，拿回離地高度、推薦結果、投放前確認結果。M2 只要把 TCP、MAVLink、UDP 接上去，M3 換成真的 Gazebo 深度，判斷規則都不用改。

同時做橋接程式會共用的**降採樣**，以及**合成深度**產生器，用來跑 §14 裡不需要網路和 Gazebo 的場景。

## User Stories

### 高度

1. 身為操作員，我要看到相機到正下方地面的垂直距離 `agl`，這樣屋頂、坑底上空也知道真的離地多高。
2. 身為操作員，我要在量不到地面時看到「量不到」而不是錯的數字，這樣不會被誤導。
3. 身為操作員，我要在傾斜時仍然看到高度，這樣調整姿態時有參考。
4. 身為操作員，我要在 12 m、18 m 高時仍有 `agl`，這樣知道是太高而不是壞掉。

### 推薦投放點

5. 身為操作員，我要按「推薦」就拿到附近可以投放的點，這樣不用自己找。
6. 身為操作員，我要推薦的點離我最近，這樣飛過去最快。
7. 身為操作員，我要推薦點的周圍也合格，這樣無人機停得不準也沒關係。
8. 身為操作員，我要推薦避開坑、縫、屋頂邊、牆、站著的人和石頭，這樣物資撿得到、不會傷人。
9. 身為操作員，我要按「換一個」時拿到明顯不同的點，這樣不用按很多次才離開同一個地方。
10. 身為操作員，我要按「換一個」被拒絕（例如當下傾斜）之後，那一點也不再出現，這樣不用重按。
11. 身為操作員，我要被確認過不合格的點 5 分鐘內不再被推薦，這樣不會來回飛。
12. 身為操作員，我要 Gazebo 重置後不會被舊的排除點影響，這樣重來一次是乾淨的。
13. 身為操作員，我要找不到時知道原因（太高、太低、傾斜、地形、量不到、都被排除、沒有資料），這樣知道下一步做什麼。
14. 身為操作員，我要正下方剛好量不到（水面、深坑）時仍然能推薦旁邊的點，這樣不會卡住。
15. 身為操作員，我要資料過期時馬上被告知，這樣不會相信舊的結果。
16. 身為 server／XR 開發者，我要推薦點的機身位移、世界座標、地面高度和像素位置，這樣可以下指令和疊圖。
17. 身為 server／XR 開發者，我要推薦點的世界座標就是機身中心要飛到的位置，這樣不用自己補償相機偏移和機頭方向。
18. 身為 server／XR 開發者，我要找不到時拿到各原因的數量，這樣可以除錯。
19. 身為操作員，我要在同一份資料上每次得到同一個推薦點，這樣結果可以相信。

### 投放前確認

20. 身為操作員，我要在投放高度按「確認」知道正下方能不能投放，這樣投放前有最後一次檢查。
21. 身為操作員，我要確認看 10 幀而不是 1 幀，這樣單幀的雜訊不會左右結果。
22. 身為操作員，我要還在移動時被提醒，這樣不會邊飛邊丟。
23. 身為操作員，我要在太高時被提醒先下降，這樣不會在搜尋高度就當成合格。
24. 身為操作員，我要在太低、看不到整個外圈時被提醒，這樣不會把沒看到的地方當成安全。
25. 身為操作員，我要不合格時看到最主要的原因，這樣知道要換地點、調高度還是停穩。
26. 身為操作員，我要收幀途中再按一次時只看到新的結果，這樣不會混淆。
27. 身為操作員，我要深度太慢或中斷時在 1.5 秒內得到答案，這樣不會一直等。

### 開發與驗收

28. 身為橋接程式的開發者，我要跟合成深度用同一個降採樣函式，這樣 M1 的結果在 M3 仍然成立。
29. 身為開發者，我要不用網路和 Gazebo 就能跑 §14 的大部分場景，這樣板子到之前就能驗完。
30. 身為開發者，我要核心的時間從外面給，這樣逾時和過期可以在測試裡直接驗，不用真的等。
31. 身為開發者，我要結果裡有每個搜尋位置的判斷，這樣可以算誤擋、找出為什麼沒選某一點。
32. 身為開發者，我要 PC 和 H1V1 在同一份資料上得到一樣的判斷，這樣 M5 只要看效能。
33. 身為開發者，我要 §11 的參數都從設定檔來，這樣 M4 的實驗不用改程式。
34. 身為負責 M4 的人，我要設定檔填量到的落地偏移，程式自己算外圈寬，這樣不會算錯或忘了多加一格。
35. 身為組員，我要 dev_board_spec、discussion、roadmap 跟程式一致，這樣不會照舊的數字做。

## Implementation Decisions

### 討論決定（2026-11-24）

| 題號 | 決定 |
| ---- | ---- |
| Q1 | 反投影用 `(u+0.5−cx)/fx`、`(v+0.5−cy)/fy`；設定檔的 cx、cy 不變。投影得到的 u、v 是連續座標，`pixel_u`、`pixel_v` 無條件捨去取整數。前提是光軸在影像正中央，M3 用地標驗 |
| Q2 | 誤擋只算「Z＋外圈＋外圈外面一格都不是 0 個點」的位置。搜尋範圍和演算法不變 |
| Q3 | `r = ceil(落地偏移 / s)·s + s`。落地偏移 0.5 m → r = 0.75 m |
| Q4 | 回放紀錄移到 M2；核心回傳完整結果，M2 才有東西可以存 |
| Q5 | §14 不需要網路和 Gazebo 的場景都放進 M1；M2、M3 用真資料複驗 |
| Q6 | 誤擋和漏判在雜訊 0 和 2 cm 各驗一次。2 cm 是加在 640×480 深度上的固定 stddev，再降採樣；固定亂數種子；σz 維持 0 |
| Q7 | 外圈滑動角不做 |
| Q8 | 收到 `exclude_last` 就先排除上一次推薦的點，再做前置檢查。被拒絕也算排除 |

### 模組

- **降採樣**（§2）：輸入 640×480 的 float 公尺 z-depth、near、far，輸出 uint16 公釐。每邊縮小倍數由輸入輸出的大小決定（設定檔允許 320×240）。「有效像素少於一半」和「第 `n/2` 個」照 §2。不依賴設定檔物件，讓橋接程式可以單獨連結。
- **判斷核心**：一個物件，從 `Config` 建立，不開執行緒、不讀時鐘、不碰網路，也不保證可以多執行緒同時呼叫。內部的內插、細格、`evaluate`、搜尋、排除清單、drop_check 狀態都不公開。
  - 輸入事件：姿態、位置（都帶 `time_boot_ms`）、深度幀（`frame_id`、sim time、尺寸、公釐資料）、推薦請求（`request_id`、`exclude_last`）、確認請求（`request_id`）、時間前進。每個事件都帶本機單調時鐘的「現在」。
  - 輸出：每個事件回傳這次產生的結果，可能是空的。種類是高度、推薦結果、確認結果，欄位名稱和可為空的規則照 §9.2 的 `payload`，不含傳輸用的外層、`request_session_id` 和 `ack`。高度另外帶資料狀態（`ok`／`no_depth`／`no_px4`，判法同 §9.2 的 heartbeat `state`），M2 的 heartbeat 直接用；`fps` 由 M2 的接收端算。
  - 推薦結果另外附診斷資料：每個位置的中心、判斷（合格或失敗原因）、外圈外面一格是否都有點。確認結果另外附每一幀的結果。診斷資料不會進 JSON。
- **合成深度**：獨立的函式庫，連結降採樣；開發板主程式不連結它。M2 的回放程式會用到。場景由一個（可傾斜的）地面、長方體凸起、長方形直壁坑組成，加上相機姿態、`t_cam`、雜訊 stddev 和亂數種子；射線投射產生 640×480 z-depth。也能把降採樣後指定區域的像素改成 0。
- **設定檔**：`zone.ring_width_m` 改名為 `zone.landing_offset_m`（值 0.5 不變，暫定），載入時照 Q3 算出外圈寬和格數。其他欄位不變。
- **編譯選項**：所有目標加 `-ffp-contract=off`，避免 aarch64 的 GCC 把乘加合併，造成門檻附近的結果跟 PC 不同。

### 行為上的補充（dev_board_spec 沒寫清楚的地方）

- **等待內插的幀**：等待中的那一幀不會被新的幀取代；它後面最多再留最新的一幀。否則姿態一直慢一點時，每一幀都會在等待中被換掉。
- **資料過期**（§5）放在核心：`no_depth`、`no_px4` 的判斷、500 ms 沒有可用幀、drop_check 1.5 秒逾時都用事件帶入的「現在」計算。
- **推薦用的幀**：照 §8.1 用最新一幀。它還在等內插就等它的結果；它不能用就等下一個能用的幀，最多 500 ms（§5）。不會退回用更舊的幀。
- **上一次推薦的點**：最近一次 `ok=true` 的推薦點；被排除之後就清掉。中間有失敗的推薦不影響它。
- **排除的時間**：drop_check 用最後一幀的 sim time，`exclude_last` 用最後已知的 sim time。
- **sim time 倒退**（§5）：除了清空 PX4 緩衝、排除清單和上一次推薦的點，也丟掉等待中的幀、還沒用掉的最新一幀，以及 drop_check 已收的幀（1.5 秒的期限不變）。
- **規則 B**：等價寫法是「外圈最外面一圈有 LOW 或 UNKNOWN 的格子，而且它緊貼的外面那格是 LOW、UNKNOWN 或 0 個點」。區內任何一格要緊貼外面，就一定在最外面一圈，所以不用找連通區。
- **同距離的推薦點**：margin、距離都相同時，用固定的順序選。距離用格數的整數平方比較，不用浮點數。
- **平面擬合無解**（點共線）：當成 `hole`，偏安全。
- **無效像素的射線沒有往下打到地面**：忽略，不計入任何細格。
- **`agl`、`depth_m` 的中位數**：偶數個時取中間兩個的平均，跟 `h_med` 相同。
- **排除半徑**：維持 2 m。

## Testing Decisions

- 好的測試只看外部行為：餵事件、看結果。不測細格、Moments、連通區這些內部東西。
- **接縫**（使用者 2026-11-25 同意）：
  1. **判斷核心**：輸入事件 → 結果。絕大多數測試在這裡，用合成深度。
  2. **降採樣**：因為橋接程式也要用，單獨測。
  - 另外沿用既有的設定檔接縫，測 `landing_offset_m` 的進位。
- 合成深度是測試工具，用已知答案檢查：正下方深度、已知像素的落點、傾斜和 `t_cam` 下的落點。
- 單一位置的判斷透過 drop_check 驗（同一個場景送 10 幀）；搜尋的判斷用推薦的診斷資料驗。
- **先例**：`tests/test_config.cpp`（doctest、讀真的設定檔、`SUBCASE`）。
- 測試在 `pc-debug`（ASan＋UBSan）、`pc-release`，以及 `h1v1` preset＋qemu 都要過。場景測試的預期用 `ok`、`reason` 比較，數值給容差。
- 推薦點都在 0.25 m 的格點上，所以座標不能只看推薦點的誤差。用「搜尋到的位置集合」驗：高度選在畫面邊緣離格線 1 cm 以上的地方，集合要跟測試自己用幾何算出來的完全相同（傾斜時避不開格線，只比較不受「離格線 5 mm 內的像素」影響的位置）。半個像素、`t_cam`、傾斜錯了，集合都會變。任意地標的座標誤差留到 M3。

### 單元測試

- 降採樣：inf、−inf、NaN、−1 m、0.05 m、25 m、70 m → 0；5 m → 5000；8 個 3 m＋8 個 13 m → 13000；只有 7 個有效 → 0
- 設定：落地偏移 0.35 m → r 0.75 m、3 格；0.5 m → 0.75 m；`Zw` 1.2 m → 1.5 m
- 內插：yaw 179° 到 −179° 取中間 → ±180°；170° 到 −170° 取 1/4 → 175°。透過推薦點的世界座標觀察
- 像素中心、`t_cam`、姿態：平地 7.4 m，水平、roll 3°、pitch 3°、`t_cam` 往右 0.15 m，搜尋到的位置集合跟幾何算的相同。水平而且 `t_cam` = 0 時要前後、左右對稱（差半個像素時，7.4 m 高左右會差一排）
- 世界座標：同一個場景，機頭朝北、東、南、西，`north`、`east` 等於 `無人機 NE + Rz(yaw)·(forward, right)`；`down_m` 等於無人機的 down＋`o.z`＋`depth_m`
- 像素：穿過 640×480 的像素 (`pixel_u`, `pixel_v`) 中心的射線打到地面的位置，跟 Z 中心的水平距離小於一個像素的寬度（7.5 m 高約 2.3 cm）
